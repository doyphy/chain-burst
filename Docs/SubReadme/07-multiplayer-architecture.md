## 7 멀티플레이 구조

**리슨 서버 · 서버 권위를 전제로 설계함.** 호스트가 곧 서버라서 방을 여는 사람과 들어가는 사람의 경로가 처음에만 갈리고, 로비에 도착한 뒤로는 전원이 같은 월드를 공유함.

접속은 **로그인 → 세션 → 접속** 세 단계가 차례로 쌓인 구조이고, 이 문서는 그 흐름을 순서대로 따라감.

접속 관련 클래스는 셋뿐임.

| 클래스 | 역할 |
|---|---|
| `UCBAuthSubsystem` | 온라인 모드를 고르고 **계정 ID 를 확보**. 제공자(LAN / EOS) 차이를 여기서 끝냄 |
| `UCBSessionSubsystem` | **방 정보(세션)와 실제 접속(travel)** 을 모두 담당. 접속 실패 처리도 여기 |
| `UCBOnlineSession` | 엔진의 기본 복귀 경로를 가로채는 얇은 어댑터 |

둘 다 **게임 인스턴스 서브시스템**임 - 맵을 넘어 살아남아야 접속 실패 신호를 받을 수 있기 때문.

---

### 7.1 멀티플레이 접속 전체 흐름
<img src="../img/Multiplay/접속전체흐름.png" width="750">

**메인 메뉴는 세션 밖이고, 로비부터가 세션 안임.**

- **세션 밖 (메인 메뉴)** - 단독 실행. 여기서 로그인을 하고 방을 만들거나 찾음.
  - `UCBAuthSubsystem` 이 LAN / Online 버튼을 받아 계정 ID 를 확보
  - `UCBSessionSubsystem` 이 그 계정으로 세션을 생성하거나 검색 · 참가
- **세션 안 (로비 · 게임플레이)** - 복제되는 월드. 각 레벨의 게임모드가 이어받음.
  - `ACBLobbyGameMode` - 로비 인원을 집계해 세션 광고를 갱신하고, 게임 시작을 처리
  - `ACBGameplayGameMode` - 게임 중에는 새 접속을 거부
- 경로가 갈리는 것은 **메인 메뉴 → 로비 구간뿐**임. 호스트는 `OpenLevel` 로 직접 열고, 참가자는 `ClientTravel` 로 붙음. 로비에 도착한 뒤로는 전원이 함께 움직임.

### 7.2 로그인 과정
<img src="../img/Multiplay/로그인과정.png" width="750">

**세션 작업에 필요한 계정 ID 를 확보하는 단계.** 제공자마다 로그인의 의미가 달라서, 그 차이를 `UCBAuthSubsystem` 하나에 가둠.

- 온라인 모드는 **설정 파일이 아니라 메인 메뉴 버튼으로 고름.** LAN 버튼과 Online 버튼이 각각 `RequestLogin()` 을 다른 모드로 호출함.
- **요청 가드** - 진행 중이면 무시, 같은 모드면 무시, 다른 모드면 비우고 새로 시작.
  - 로그인 콜백이 비동기라, 그 사이 상태를 갈아엎으면 **뒤늦게 도착한 콜백이 새 상태를 덮어씀.**
- **LAN (Null)** - 로그인 절차가 없음. 플랫폼 유저가 생길 때 자동 등록된 계정을 꺼내 씀.
- **Online (EOS)** - 서비스 확보 → Device ID 생성 → 그 자격증명으로 로그인, 이 순서를 지켜야 함.
  - 순서가 뒤집히면 플랫폼이 둘 생겨 **"로그인은 됐는데 세션이 계정을 못 찾는"** 상태가 됨.
- 성공하면 계정 ID 를 `CachedAccountId` 에 보관하고 상태를 방송함. 세션 작업은 전부 이 값을 요구함.

### 7.3 세션 생성 과정
<img src="../img/Multiplay/세션생성과정.png" width="750">

**호스트 쪽.** `UCBSessionSubsystem::Local_CreateAndHostSession()` 하나가 로비 레벨 · 방 이름 · 정원을 받아 시작함.

| 단계 | 하는 일 |
|---|---|
| 요청 가드 | 로그인 여부를 검사하고 세션 인터페이스와 계정 ID 를 조회 |
| 세션 속성 채우기 | 검색 측이 읽어갈 값을 전부 여기서 실음 |
| 세션 생성 요청 | 비동기. 로비 레벨과 정원은 `PendingLobbyLevel` · `PendingMaxPlayers` 에 보관 |
| 생성 성공 콜백 | 보관해둔 값으로 `Local_HostLobby()` 를 불러 리슨 서버로 엶 |

**세션 속성에 싣는 값**

- **버킷** - EOS 검색 필터. 네트워크 호환성이 다른 빌드끼리 방이 보이지 않게 가름
- **호스트 주소** - 참가 측이 그대로 접속할 주소
- **방 이름** - 목록에 보일 이름
- **현재 인원** - 생성 시 1(호스트)로 미리 채움. 로비가 열리기 전에 검색되면 0으로 보이기 때문

**리슨 오픈에서 놓치기 쉬운 것**

- `listen` 옵션이 빠지면 **에러 없이 단독 실행이 됨.** 아무도 접속하지 못하는 상태가 조용히 만들어짐.
- LAN 모드는 URL 옵션을 하나 더 붙여야 함 - 없으면 넷 드라이버가 EOS 경로로 들어가 P2P 주소를 요구하고, **방 만들기 자체가 실패함.**
- 정원은 URL 옵션으로 넘겨 서버가 접속 거부 판정에 씀.

`Local_HostLobby()` 는 공개 API 라 **세션 없이 그것만 불러도 방이 열림.** 세션 계층은 그 앞에 얹힌 것뿐임.

### 7.4 세션 검색 과정
<img src="../img/Multiplay/세션검색과정.png" width="750">

**참가 측.** `Local_FindSessions()` 가 최대 결과 수를 받아 시작하고, 완료 콜백이 결과를 표시용 목록으로 옮김.

- **검색 조건 구성** - 버킷 ID 를 필터로 넣음. 조건이 하나도 없으면 EOS 가 **빈 쿼리로 보고 거부함.**
  - 생성 쪽만 버킷을 자동으로 채워주기 때문에, 방 만들기는 되고 **검색만 실패하는** 모양이 됨.
- **검색 성공 콜백** - 세션마다 표시용 항목을 만들어 `FoundSessions` 에 담고, 참가에 쓸 세션 ID 는 `FoundSessionIds` 에 같은 순서로 보관. 끝나면 검색 완료를 방송해 목록 위젯이 갱신됨.
- 표시 항목을 만드는 곳을 한 함수에 모음 - **목록 표시와 참가 가드가 같은 기준**을 쓰게 하려는 것.

#### ⭐ 인원은 왜 직접 실어 보내나

엔진이 알려주는 '열린 커넥션 수'는 **멤버 목록에서 계산되는데, 그 목록을 채우는 제공자가 사실상 없음.** 결과적으로 언제나 정원과 같은 값이 나와서 인원 표시에 쓸 수 없음.

- 그래서 **호스트가 로비 인원이 바뀔 때마다 직접 세어 광고함** (`Auth_UpdateAdvertisedPlayerCount()`, 로비 게임모드가 호출).
- 재광고는 필요 없음 - 검색 응답은 질의가 올 때마다 호스트의 현재 세션 값으로 만들어지므로, 값을 고쳐두면 다음 검색부터 그대로 잡힘.

검색 결과는 **스냅샷임.** 클릭과 접속 사이에 남이 들어갈 수 있어서, 정원 판정의 권위는 서버에 둠.

### 7.5 세션 참가 과정
<img src="../img/Multiplay/세션참가과정.png" width="750">

**참가 측.** `Local_JoinFoundSession()` 이 목록에서 고른 인덱스를 받고, 참가에 성공하면 세션 속성에서 호스트 주소를 읽어 `Local_JoinServerByAddress()` 로 넘김.

- **참가 직전 재확인** - 목록에서 사라졌거나 정원이 찼으면 멈추고 새로고침을 안내함.
  - 다만 이건 **새 조회가 아니라 마지막 검색 스냅샷을 다시 읽는 것**임. 검색 이후 시작된 방은 여기서 걸러지지 않음.
  - 헛된 접속 시도를 줄이고, 인덱스가 어긋나 엉뚱한 방에 붙는 사고를 막는 용도.
- 주소를 넘긴 시점에 **세션 계층은 손을 뗌.** 그 뒤는 순수한 접속 경로임.

#### ⭐ 정원 판정은 세션이 아니라 서버가 한다

- 검색 결과는 스냅샷이라 권위가 없고, 엔진의 '참가 가능' 값은 위 이유로 **언제나 참**이라 판정에 쓸 수 없음.
- 그래서 마지막 한 자리를 둘이 노려도 **접속 시점에 서버가 한 명만 받음.** 목록의 정확도와 무관하게 안전해짐.
- 거부 사유는 문자열로 실려 옴.
  - 정원 초과 - 엔진이 넣는 사유
  - 진행 중인 매치 - **게임플레이 레벨에 새로 접속한다는 것 자체가 "매치가 이미 시작됐다"는 뜻**이라 별도 상태 판단이 필요 없음
  - 클라이언트가 그 문자열을 읽어 보여줄 문구를 가름 (양쪽이 같은 값을 보도록 상수 한 곳에서 공유)

> 💡 로비에서 함께 출발한 인원은 영향받지 않음. seamless travel 로 이관되므로 접속 승인 절차를 타지 않음.

### 7.6 접속 실패 처리
<img src="../img/Multiplay/접속실패과정.png" width="750">

**실패는 두 델리게이트로 들어오고 한 함수로 모임.** `UCBSessionSubsystem` 이 생성될 때 엔진의 네트워크 실패 · 맵 이동 실패 델리게이트를 구독해둠.

| 입구 | 언제 | 하는 일 |
|---|---|---|
| `Local_HandleNetworkFailure()` | 서버 - 리슨 서버를 열지 못함 / 클라 - 접속 실패 · 연결 끊김 | 함께 넘어온 실패 종류에 맞는 사유 문구를 담음 |
| `Local_HandleTravelFailure()` | 맵 이동 실패 | 맵을 여는 데 실패했다는 문구를 담음 |

두 입구가 만든 사유는 `Local_HandleConnectionFailure()` 로 넘어가고, 거기서 **레벨을 옮길지**가 갈림.

- **현재 레벨을 유지할 때** - 사유를 그대로 방송함. 살아 있는 위젯이 받아 모달을 띄움.
  - 참가 실패는 메인 메뉴에 머문 채 일어나므로, 입력해 둔 값이 날아가지 않음.
- **메인 메뉴로 돌아갈 때** - 사유를 따로 보관해두고 이동함. 메인 메뉴에서 꺼내 모달을 띄움.
  - 레벨을 넘기면 방송을 받을 위젯이 그 순간에 없기 때문. 반대로 제자리 실패까지 보관하면 **다음에 정상적으로 메뉴에 들어왔을 때 지난 사유가 뒤늦게 뜸.**

#### ⭐ 엔진 기본 복귀 경로를 가로챈다

**우리가 아무것도 하지 않아도** 커넥션이 닫히면 엔진이 기본 맵을 다시 로드함. 그 경로가 `UOnlineSession::HandleDisconnect()` 하나로 모이므로, `UCBOnlineSession` 으로 그 자리를 대신 차지함.

- 엔진이 복귀하려 할 때 **"지금 레벨을 유지해야 하느냐"를 세션 서브시스템에 물어봄.**
  - `true` - 엔진 자동 복귀를 중간에서 끊음 (현재 레벨 유지)
  - `false` - 엔진 기본 경로를 그대로 따름 (기본 레벨로 이동)
- 판단은 서브시스템이 하고 이 클래스는 전달만 함 - **접속과 복귀에 관한 결정을 한 곳에 모으기 위함.**
- 끊지 않으면 참가 실패 시 **모달이 뜨자마자 위젯과 함께 사라져** 아무 말 없이 메뉴로 돌아감.
- 반대로 인게임 끊김은 막지 않음. 서버가 사라진 월드에는 머물 수 없고, 커넥션이 닫힌 채로 있으면 실패가 매 프레임 다시 방송되어 모달이 무한히 뜸.
