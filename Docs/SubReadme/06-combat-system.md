## 6 전투 시스템

### 6.1 전투 시스템 구조
<img src="../img/Combat/전투시스템구조.png" width="750">

**무기는 붙을 위치와 트레이스용 두 지점만 내주고, 스폰 · 수명 · 히트 판정 · 상태는 전부 컴뱃 컴포넌트가 가짐.**

- 전투 시스템은 **컴뱃 컴포넌트**와 **무기 액터** 두 축으로 이뤄짐. 둘 다 캐릭터 계열(플레이어 / 고급 적 / 일반 적)에 맞춰 자식을 두지만, **자식은 멤버 없이 로직이 갈릴 자리만 확보**해둔 상태임.
- 역할 분담이 단순함.
  - 컴뱃 컴포넌트 - 무기 저장소 · 수명 · 트레이스 · 히트 검증 · 전투 상태 · 콤보를 전부 소유
  - 무기 액터 - 어디에 붙는지(소켓)와 트레이스가 읽을 두 지점(Root · Tip)만 제공. 데미지도 콜리전도 갖지 않음
- 둘을 잇는 데이터는 **무기 데이터 에셋 하나**. 로드아웃에 등록해두면 캐릭터 초기화 때 컴뱃 컴포넌트로 전달되어 스폰 · 부착 · 등록까지 이어짐.
- 어빌리티는 무기 트레이스 조각을 통해 컴뱃 컴포넌트의 API 만 호출함 - 무기를 직접 찾지도, 상태 태그를 직접 붙이지도 않음.

> 🔎 공격 어빌리티 쪽 구조(활성화 가드 · 콤보 전진 · 종료 경로)는 [2 어빌리티 아키텍처](02-ability-architecture.md) 참고

#### 6.2.1 무기 소켓
<img src="../img/Combat/무기소켓.png" width="750">

**무기는 소켓 데이터를 관리하고, 무기 부착과 소켓 위치 API 를 제공함.**

- 무기가 하는 일은 **부착**과 **위치 제공** 둘뿐. 데미지 · 콜리전 · 히트 판정은 갖지 않음.

- 무기의 Root 와 Tip 소켓을 설정 - 트레이스 범위에 사용

#### 6.2.3 무기 소켓 데이터 에셋

모든 무기의 소켓 이름을 모아둠 (외부 조회용)
- 무기 클래스에서 데이터 에셋을 읽어서 소켓 타입만 맞춰주면 소켓 이름 반영해줌 (에디터용)
- **소켓 타입은 무기 종류가 아니라 "어느 슬롯을 점유하는가"** 를 뜻함. 쌍수 단검이 `Dagger (Left)` / `Dagger (Right)` 로 나뉘는 이유임.
- 캐릭터마다 스켈레톤 소켓 이름이 다를 수 있어 Chaser / Outlaw / Rogue 별로 에셋을 따로 둠.

#### 6.2.4 무기 데이터 에셋
<img src="../img/Combat/무기데이터에셋.png" height="500">

**실제 로드아웃에 무기를 등록할 때 무기 데이터 에셋에 담아서 등록**

| 항목 | 쓰임 |
|---|---|
| 소켓 타입 | 이 무기가 점유할 슬롯. 등록 중복 검사 기준 |
| 무기 클래스 | 스폰할 무기 액터 (일반 무기 / 본체 무기) |
| 무기 공격력 | 등록 시 공격력 GE 로 시전자의 `AttackPower` 에 더해짐 |
| 피격 큐 태그 | 무기 트레이스 적중 시 피격자에게 실행할 연출 큐 |
| 공격력 GE | 등록 시 ASC 에 적용할 공격력 이펙트 |

- 무기를 하나 더 늘릴 때 **데이터 에셋만 만들어 로드아웃에 넣으면 됨** - 컴뱃 컴포넌트도 어빌리티도 수정하지 않음.

### 6.3 본체 무기
<img src="../img/Combat/본체무기.png" width="750">

**무기를 들지 않는 몬스터(발톱 · 이빨)도 '무기'로 등록해서 기존 전투 파이프라인을 그대로 씀.**

컴뱃 컴포넌트의 기능(무기 유효성 · 트레이스 · 히트 검증 · 공격력 GE)이 전부 **등록된 무기 하나**에 걸려 있음. 그래서 맨손 몬스터를 위해 무기 개념을 우회하는 것보다, **트레이스 소스만 바꾼 무기**를 하나 등록하는 쪽이 변경 범위가 훨씬 작았음.

- 재정의하는 것은 **위치 getter 둘뿐** - 무기 메시 대신 오너 캐릭터의 스켈레탈 메시에서 소켓을 조회함.
- 등록 · 공격력 GE · 트레이스 루프 · 히트 검증은 **한 줄도 바뀌지 않음.**
- 오너 메시는 스폰 시 지정된 Owner 로 찾음 - Owner 는 복제되므로 서버 · 클라이언트가 같은 경로를 타고, 매 틱 조회를 피해 약참조로 지연 캐싱함.
- 소켓을 점유하지 않으므로(`None`) 등록 중복 검사에서 제외됨. 양 앞발처럼 부위가 둘이면 2개까지 등록 가능.

#### 💡 설계상 주의 세 가지

| 주의 | 이유 |
|---|---|
| **빈 메시 무기로는 대체할 수 없음** | 소켓 없는 빈 메시의 소켓 조회는 컴포넌트 자기 위치를 돌려줌 → Root == Tip == 부착 지점이 되어 판정이 사라짐. 그래서 빈 메시 소켓이 아니라 **스켈레탈 메시 소켓**을 씀 |
| **두 소켓은 반드시 떨어뜨릴 것** | 트레이스는 Root → Tip 소켓 사이를 판정 구간으로 씀. 두 지점이 같으면 분할마다 같은 트레이스를 중복 발사하고 판정 면이 점으로 쪼그라듦. 발톱이면 손목 / 발톱 끝처럼 벌려 잡을 것 |
| **소켓 이름 오타는 조용히 실패함** | 못 찾으면 캐릭터 원점이 반환되어 엉뚱한 곳에서 판정이 남 → 오너 메시를 처음 찾은 시점에 이름 존재를 1회 검증해 경고를 남김 |

본 이름을 그대로 써도 됨 - 스켈레탈 메시의 소켓 조회는 소켓뿐 아니라 본 이름도 받음. 다만 본은 관절 위치라 발톱 끝 같은 지점은 소켓을 따로 심는 편이 정확함.

### 6.4 무기 등록과 수명
<img src="../img/Combat/무기등록과수명.png" width="750">

**등록은 로드아웃이 부르고 서버만 수행하며, 정리는 컴포넌트가 끝나는 시점 한 곳이 책임짐.**

로드아웃 안에 무기 데이터 에셋을 넣으면 로드 시 컴뱃 컴포넌트의 무기 등록 API 와 함께 넘김.

**등록 규칙**

- 최대 2개 - 쌍수 무기는 왼손 · 오른손을 **별개로 등록**함.
- 중복 검사 기준은 **소켓 점유** - 한 소켓엔 무기 하나. 소켓을 점유하지 않는 무기(본체 · 소환형)는 검사에서 제외.
- 무기 BP 와 데이터 에셋의 소켓 타입이 다르면 경고를 남김 (등록은 계속 진행) - 설정 실수를 런타임 전에 알아채기 위함.

**수명 정리**

- 무기는 부착으로도 소유(Owner)로도 파괴가 전파되지 않음. 캐릭터가 사라져도 **월드에 그대로 남으므로** 컴포넌트가 직접 파괴함.
- 캐릭터의 파괴 시점이 아니라 **컴포넌트가 끝나는 시점**에 정리하는 이유 - 명시적 파괴뿐 아니라 맵 전환 · 종료까지 덮고, 무기 저장소와 수명이 한 클래스 안에 모임.
- 무기는 복제 액터라 서버에서 파괴하면 전 클라이언트에서 함께 사라짐.

#### 왜 소유 폰이 파괴될 때 직접 정리해야 하나

**플레이어의 ASC 는 PlayerState 소유라 폰을 파괴해도 살아있음.** 폰이 바뀌어도 GE 와 루스 태그는 그대로 남아서, 걷어내지 않으면 다음 폰까지 이월됨.

- **공격력 GE** - 남기면 죽을 때마다 · 캐릭터를 바꿀 때마다 새 폰이 적용하는 GE 가 그 위에 쌓여 **공격력이 무한히 올라감.**
- **전투 상태 태그** - 남기면 새 폰이 무기를 칼집에 둔 채 전투 상태로 시작할 수 있음. 이때 장착 어빌리티는 "이미 전투 상태"로 판단해 조기 반환하므로 **무기가 손에 붙지 않음.**
- 걷어내는 주체는 **직접 붙인 인스턴스뿐임.** 복제로 태그만 받은 시뮬레이티드 프록시는 제거 주체가 아님.

### 6.5 컴뱃 컴포넌트
<img src="../img/Combat/컴뱃컴포넌트.png" width="750">

**한 클래스가 네 구획으로 나뉨. 무기는 서버, 트레이스는 로컬, 검증은 서버, 콤보는 각자 예측.**

| 구획 | 제공하는 API | 성격 |
|---|---|---|
| 무기 | 무기 등록 / 무기 보유 검사 / 전체 파괴 / 공격력 GE | 서버 전용 (`Auth_`) |
| 전투 상태 | 전투 모드 설정 / 조회 / 진입 · 이탈 처리 | 진입점은 설정 함수 하나 |
| 트레이스 · 히트 | 트레이스 시작 / 틱 / 종료 / 히트 서버 전송 | 로컬 감지 → 서버 검증 |
| 콤보 | 콤보 전진 / 리셋 / 현재 인덱스 조회 | 비복제 · 각자 예측 |

- **무기 등록**은 검증 → 스폰 → 부착 → 등록 순으로 진행하고, 무기 보유 검사는 공격 · 장착 어빌리티의 활성화 가드로 쓰임.
- **전투 상태**는 설정 함수 하나가 유일한 진입점. 그 안에서 무기 부착(손 / 칼집)과 상태 태그 추가 · 제거를 **함께** 처리함.
  - 어빌리티는 이 함수만 호출하고 태그를 직접 건드리지 않음 - 부착 상태와 태그가 다른 곳에서 따로 갱신되어 어긋나는 것을 막기 위함.
- **트레이스**는 노티파이 스테이트가 태그 이벤트를 쏘면 무기 트레이스 조각(`UCBFragment_WeaponTrace`)이 받아서 시작 · 종료를 부름. 컴포넌트는 판정만 수행함.
- **콤보**는 인덱스와 진행 중인 액션 태그만 보관함. **타이머가 없고**, 리셋 시점은 어빌리티가 정함.

**네 구획이 공유하는 상태는 전부 private**

- 무기 목록 - 부착 · 트레이스 · 검증이 전부 이걸 순회함
- 트레이스 진행 여부 · 대기 중인 히트 · 이미 맞은 액터 - 트레이스 한 번 동안만 유효한 로컬 상태
- 콤보 인덱스와 진행 중인 액션 태그
- 오너 메시 · ASC 약참조 캐시 - 부착마다 다시 찾지 않기 위함

Tick 은 꺼진 채로 시작해 **트레이스 동안만 켜짐.** 네 구획 중 네트워크로 나가는 것은 **무기 목록과 전투 태그뿐**이고, 콤보 · 트레이스 상태는 복제하지 않음.

> 🔎 콤보 예측과 거부 롤백은 [2.5 Chaser 공격 어빌리티](02-ability-architecture.md#25-chaser-공격-어빌리티-ucbchaserattackability) 참고

### 6.6 트레이스 검사 방식
<img src="../img/Combat/무기트레이스.png" width="750">

**콜리전 없이 매 틱 직접 훑음.** 무기의 Root 와 Tip 소켓 사이를 여러 점으로 나누고, 각 점의 지난 프레임 → 이번 프레임 구간을 **세로로 선 캡슐**로 메워 **프레임 사이로 빠져나가는 히트를 없앰.**

- 무기에 오버랩 이벤트를 달지 않음 - 판정 시점과 구간을 몽타주가 정하고, 무기는 위치만 내주는 구조를 유지하기 위함.
- 분할 개수와 반지름은 에디터 노출 값. **트레이스 소켓 사이가 먼 긴 무기일수록 분할을 늘려** 점 간격을 좁히고, 짧은 무기는 줄임.

#### 세로로 선 캡슐 - 가로는 칼날, 세로는 몸 높이

- 가로(XY)는 소켓 구간을 반지름(`TraceRadius`) 그대로 따라가고, 세로(Z)는 **공격자 캡슐 바닥 ~ 머리끝**까지 넓힘. (소켓이 몸 밖으로 나가면 거기까지)
- 칼날이 쓸고 간 얇은 면만 판정하면 **키 작은 적이 스윙 아래로 빠짐.** 반지름을 키우면 모든 방향으로 뚱뚱해져 **눈에 띄게 빗나간 공격이 맞음.** 가로 오차는 바로 보이고 세로 오차는 거의 보이지 않아서 **세로만 넓힘.**
- 높이를 고정 값으로 두지 않고 공격자 캡슐에서 유도함 - 큰 보스는 자동으로 커지고, 새 캐릭터를 추가해도 맞출 값이 없음.

#### 전용 `Weapon` 채널

- 이동용 `Pawn` 채널과 분리해 **"이동을 막는가"와 "맞을 수 있는가"를 따로 끌 수 있게 함.** (시체는 통과 · 판정 제외, 회피 무적은 이동은 막고 판정만 제외)
- 캐릭터는 캡슐 `Ignore` · 메시 `Overlap` → 피직스 실루엣으로 판정하고, 일직선의 여러 적을 관통해 벰. 벽 · 지형은 `Block`이라 스윕을 끊음. (→ [1.2 베이스 캐릭터](01-character-architecture.md#12-베이스-캐릭터-acbbasecharacter))

**트레이스 한 번의 수명** - 세 함수 모두 로컬에서만 작동하고, 구간은 몽타주가, 호출은 무기 트레이스 조각(`UCBFragment_WeaponTrace`)이 정함.

| 단계 | 하는 일 |
|---|---|
| 시작 | 충돌 기록 · 배칭 창을 비우고, 무기별 Root · Tip 을 이전 위치로 스냅샷 · Tick 켜기 |
| 틱 | 무기 순회 → 분할 점마다 캡슐 스윕 → 적대 · 벽 검사 → 액터당 첫 히트만 대기 목록에 적재 |
| 종료 | 마지막 Tick 이후 남은 구간을 한 번 더 훑고, 대기 중인 히트를 즉시 보낸 뒤 Tick 끔 |

- **종료 시 한 번 더 훑는 이유** - 트레이스는 프레임 단위 샘플링이라 마지막 Tick ~ 구간 종료 사이의 휘두름이 통째로 빠짐. 재생 속도(공격 속도)가 빠를수록 누락되는 호가 커짐.
- 어빌리티가 캔슬돼도 `EndAbility` → 조각의 `Stop()`이 종료 함수를 한 번 더 부름. **진행 여부 가드가 중복 호출을 흡수**해 낡은 이전 위치로 다시 훑지 않음.

**히트를 거르고 보내는 장치**

| 장치 | 역할 |
|---|---|
| 이미 맞은 액터 기록 | 한 스윙 동안 액터당 1회 · **무기 간 공유**라 쌍수도 두 블레이드로 이중 히트가 안 남 |
| 히트 배칭 | **스윙 첫 타는 즉시** 보내고, 뒤따라 걸린 대상만 0.1초 창으로 모아 RPC 하나로 보냄 |
| 벽 검사 | 공격자 중심 → 대상 중심 선이 벽에 막히면 제외. 칼날 일부가 처음부터 벽 너머에 있으면 스윕이 벽을 지나지 않아 뒤의 적이 맞는 경우를 막음 |
| 무시 목록 | 자신과 등록된 모든 무기 인스턴스를 트레이스 대상에서 제외함 |

- **배칭은 중복 방지 장치가 아님** - 중복은 맞은 액터 기록 하나가 막고, 배칭은 RPC 수만 줄임. 대가로 뒤따라 맞은 대상의 피해가 최대 0.1초 늦게 적용되는데, 맞는 쪽이 AI 인 협동(PvE)이라 감수함. (경쟁 규칙이면 간격을 0으로 두면 배칭이 꺼짐)

<img src="../img/Combat/트레이스커스텀.png" width="750">

- 무기의 Root 와 Tip 소켓 사이가 길면 분할 개수를 늘려서 트레이스 빈틈 줄이기
- 트레이스 반지름 · 분할 개수 · 채널(기본 `Weapon`) · 디버그 표시를 전부 데이터로 조정 가능

### 6.7 히트 검증 - 로컬 감지 · 서버 검증
<img src="../img/Combat/히트검증과데미지.png" width="750">

**히트 판정은 조종 중인 머신에서 하고, 서버는 그 결과를 진영과 거리로 다시 잼.**
클라이언트가 보내는 것은 **'누구를 맞췄는가'뿐**이고, 데미지 값은 서버가 만들어 적용함.

로컬에서 처리 (조종 중인 머신 - AI 는 서버가 곧 로컬이라 같은 경로를 그대로 탐)

- [ 1.히트 감지 ] - 세로 캡슐 스윕이 새 액터를 잡음. 적대 진영이 아니거나 벽에 막힌 대상은 여기서 거름 (스윙당 1회만)
- [ 2.적재 ] - 스윙 첫 타는 즉시 보내고, 뒤따라 걸린 대상만 0.1초 창으로 모아 RPC 횟수를 줄임
- [ 3.전송 ] - 타겟 데이터 핸들로 감싸 서버 RPC(`Reliable`)로 전달

서버에서 처리 (권위)

- [ 4.진영 및 거리 검증 ] - 적 진영이 아니거나 허용 거리를 넘으면 경고 로그를 남기고 버림
- [ 5.통과분만 재구성 ] - 검증을 통과한 타겟만 다시 담고, 하나도 없으면 종료
- [ 6.히트 이벤트 발행 ] - `Event.Combat.Attack.Hit` → 무기 트레이스 조각이 받아 데미지 적용. 버스트 게이지 · 적중 회복 패시브도 같은 이벤트를 받으므로, 적중 보상은 검증을 통과한 히트에만 쌓임

#### ⭐ 왜 로컬에서 감지하나 (반응성을 위해)

몽타주 재생 위치가 **머신마다 미세하게 어긋남.** 서버가 직접 훑으면 레이턴시만큼 늦은 자세로 판정해, 플레이어 화면에서 **맞은 것처럼 보인 스윙이 빗나감.**

- 그래서 **보이는 화면에서 판정**하고, 서버는 결과만 다시 잼.
- 반대로 클라이언트 필터만 믿을 수도 없음 - 트레이스가 로컬에서 돌고 결과만 올라오므로, 조작된 클라이언트가 아군이나 먼 타겟을 실어 보낼 수 있음.
- 진영 판정은 AI 타겟팅 · 퍼셉션과 **같은 전역 규칙**을 탐. 팀이 지정되지 않은 캐릭터는 중립으로 떨어져 때릴 수 없게 되므로 주의.

**서버가 재는 것은 거리 하나**

```
허용 거리    =  최장 Tip 거리 + 트레이스 범위 + 레이턴시 보정값(100)
트레이스 범위 =  max(트레이스 반지름, 공격자 캡슐 반높이)
실제 거리    =  공격자 액터 ~ 피격 액터 중심 거리
```

- Tip 이 가장 멀리 닿는 지점이라 기준으로 삼음. 쌍수는 **가장 먼 Tip** 을 써서 어느 손으로든 유효한 히트를 허용함.
- **판정 볼륨과 검증 기준은 같이 움직여야 함** - 트레이스가 세로로 몸 높이까지 넓어졌으므로 검증도 그만큼 늘림. 반지름만 더하면 키 큰 공격자의 정당한 히트를 서버가 거부함.

#### ⭐ 벽 검사는 서버 검증에 넣지 않음

- AI 는 감지 자체가 서버라 이미 권위 판정이고, 정직한 클라이언트는 벽 너머 히트를 보내지 않음.
- 서버가 다시 재면 레이턴시만큼 다른 위치로 판정해, 클라이언트 화면에서 열려 있던 사이 적이 기둥 뒤로 들어간 경우 "맞았는데 거부"가 남.
- 협동(PvE)에서는 이 손해가 부정행위 방지 이득보다 크다고 판단해, **조작된 클라이언트가 벽 너머 히트를 보낼 수 있는 것은 수용함.** 경쟁 규칙이 되면 거리 검증처럼 허용 오차를 둔 서버 벽 검사를 추가함.

#### ⭐ 6.7.1 트레이스 레이턴시 보정
<img src="../img/Combat/트레이스레이턴시.png" width="750">

- 클라이언트와 서버간의 위치가 미세하게 다르기 때문에 어디까지 보정해줄지 설정 (`HitValidationTolerance`, 기본 100)
- 클라에서 히트한 액터를 서버에서 검증할 때 공격 범위(+보정값)로 검증함.

### 6.8 영역 공격 (`UCBFragment_AreaAttack`)
<img src="../img/Combat/영역공격설정.png" width="750">

<img src="../img/Combat/영역공격노티파이.png" width="750">

**무기가 닿은 대상이 아니라 범위 안의 대상을 때리는 공격(내려찍기 · 충격파). 판정 순간 박스 오버랩 쿼리를 한 번 던짐.**

- 몽타주의 `Event.Combat.AreaAttack` 단발 노티파이가 판정 시점을 정함 - 노티파이를 여러 개 두면 그만큼 여러 번 터짐.
- 박스(`BoxExtent`)는 시전자 위치에서 `CenterOffset` 만큼 떨어진 곳에, **시전자가 바라보는 방향으로 회전**해 놓임.
- 감지는 서버에서 함 (현재 AI 전용 - AI 는 서버가 곧 로컬이라 따로 검증할 단계가 없음).

<img src="../img/Combat/영역공격결과.gif" width="750">

| | 무기 트레이스 | 영역 공격 |
|---|---|---|
| 쿼리 | 스윕 (칼날 구간이 프레임 사이에 쓸고 간 면) | 오버랩 (한 자리에 놓은 회전 박스) |
| 시점 | 구간 노티파이 스테이트 | 순간 단발 노티파이 |
| 감지 머신 | 로컬 → 서버 검증 | 서버 |
| 벽 | 채널이 `Block` 이라 스윕이 끊김 + 중심선 검사 | 끊길 경로가 없어 **라인 트레이스로 따로 검사** |
| 채널 · 진영 · 데미지 | `Weapon` 채널 · 적대만 · `Auth_ApplyDamageToTarget()` | 같음 |

#### ⭐ 콜리전 컴포넌트를 스폰하지 않고 쿼리를 쓰는 이유

- 콜리전을 스폰해 오버랩 이벤트를 받으면 결과가 **다음 물리 갱신 뒤에** 오고, 생성 순간 이미 겹쳐 있던 대상은 이벤트가 오지 않을 수 있어 따로 처리해야 함.
- 한 순간 터지는 공격에는 **호출 즉시 결과가 나오는 쿼리**가 맞음. (일정 시간 남는 장판이 생기면 타이머로 주기마다 쿼리하는 쪽을 먼저 검토)

#### ⭐ 벽 검사 시작점은 공격마다 고름

- 기본은 **판정 중심** - 터진 자리에서 퍼지는 공격(내려찍기).
- 입 · 손에서 앞으로 뿜는 공격은 **시전자 소켓**(`WallCheckSocketName`)에서 그음 - 앞으로 길게 뻗은 박스는 중심이 벽 너머에 있을 수 있어, 중심에서 그으면 시전자와 대상 사이의 벽을 못 봄.
- 소켓 이름이 틀리면 경고를 남기고 판정 중심에서 검사함.
- 대가: 시작점 → 대상 중심 한 줄만 보므로, 대상 몸 일부가 벽 밖으로 나와 있어도 중심이 벽 뒤면 맞지 않음.

### 6.9 투사체 공격 (`UCBFragment_Projectile` · `ACBProjectile`)

<img src="../img/Combat/투사체조각설정.png" width="750">

<img src="../img/Combat/투사체BP설정.png" width="750">

<img src="../img/Combat/투사체노티파이.png" width="750">


**날아가는 물체가 맞히는 공격. "언제 · 어디서 · 몇 발 · 어떤 데미지로 쏠지"는 조각이, "어떻게 날아가서 누구에게 맞을지"는 투사체 액터가 맡음.**

<img src="../img/Combat/투사체결과.gif" width="750">

**투사체 공격 방식을 다양하게 커스텀 가능**

<img src="../img/Combat/투사체결과2.gif" width="750">


#### ⭐ 발사와 비행을 나눈 이유 - 수명이 다름

- 투사체는 공격 몽타주와 어빌리티가 끝난 뒤에도 날아가 명중하고, 명중 시점에는 시전자가 이미 죽어 어빌리티가 사라졌을 수도 있음.
- 그래서 **발사 순간에 데미지 스펙을 만들어 투사체에 실어 보내고**, 명중하면 투사체가 그 스펙을 적용함 (`Auth_ApplyDamageSpecToTarget()`).
- 시전자가 먼저 파괴되면 진영 판정이 중립이 되어 아무도 맞지 않음. 시전자가 죽었어도 시체가 남아 있으면 그대로 맞음.

**발사 (서버 · 조각)**

- `Event.Combat.FireProjectile` 노티파이마다 한 번 발사 - 노티파이를 여러 개 두면 연사.
- 발사할 때마다 **그 순간의 타겟 위치로 다시 조준**함 - 연사 중 타겟이 움직여도 따라감.
- `SpawnSocketName` 위치에서 `ProjectileCount` 발을 `SpreadAngle` 부채꼴로 스폰함 (360 이면 사방으로 고르게).

**비행 (투사체 액터 · BP 설정)**

| 방식 | 설정 | 동작 |
|---|---|---|
| 직선 (`Direct`) | `InitialSpeed` (기본 1500) | 조준점을 향해 직선으로 날아감 |
| 포물선 (`Arc`) | `ArcParam` (0.1 높게 ~ 0.9 낮게) + 중력 | 조준점에 떨어지는 포물선. 이 투사체에 실제로 걸리는 중력으로 속도를 풀며, 풀 수 없으면 경고 후 직선으로 쏨 |
| 유도 | ProjectileMovement 의 Homing 설정 | 발사 때 받은 타겟을 따라감 (`MaxSpeed` 로 속도 상한 권장) |

- 수명은 기본 5초 - 빗나간 투사체가 끝없이 날아가지 않게.

**명중 판정 (서버)**

- 매 틱 지난 위치 → 현재 위치를 **루트 컴포넌트 모양**(구 · 박스 · 캡슐)으로 `Weapon` 채널 스윕 - BP 에서 루트 모양만 바꾸면 판정 모양이 바뀜.
- 적대 + ASC → 데미지 스펙 적용 + 피격 큐 → 소멸 (단일 명중) / 아군 · 중립 → 통과 / 벽 · 지면 → 소멸.
- 이동이 끝난 뒤에 판정하도록 틱 순서를 걸어, 빠른 투사체가 얇은 대상을 건너뛰지 않음.
- 투사체 자신의 콜리전은 런타임에 모두 끔 - 연출 메시가 플레이어의 무기 트레이스 · 카메라 · 영역 공격 벽 검사를 가로막지 않게.

#### ⭐ 복제 - 발사 조건만 보내고 각자 시뮬레이션

- 서버가 스폰하는 복제 액터. 클라이언트에는 **발사 속도 · 유도 대상만 최초 1회** 보내고(`COND_InitialOnly`), 각 머신이 궤적을 직접 시뮬레이션함 - 직선 · 포물선은 결정적이라 서버와 같은 궤적이 나옴.
- 유도는 타겟의 복제 위치 차이로 갈라질 수 있어 **이동 복제로 보정**함. (엔진 `PostNetReceiveVelocity` 가 비어 있어, 받은 속도를 이동 컴포넌트에 넣도록 재정의)
- 소멸은 액터 파괴 복제로 전 클라이언트에 반영됨.

### 6.10 데미지 적용

**판정 방식은 셋(무기 트레이스 · 영역 · 투사체)이지만, 데미지를 만드는 식과 적용 코드는 하나로 모음.**

- 트레이스 구간은 몽타주의 노티파이 스테이트가 정하고(→ [2.2 태그 이벤트 노티파이](02-ability-architecture.md#22-태그-이벤트-노티파이--노티파이-스테이트)), 구간 동안 걸린 히트가 서버 검증을 통과하면 무기 트레이스 조각이 받아 적용함.
- 적용 코드는 공용 함수 `UCBAbilitySystemLibrary::Auth_ApplyDamageToTarget()` 하나 - 무기 트레이스와 영역 판정이 함께 씀.

<img src="../img/Combat/공격어빌리티데미지설정.png" width="750">

**데미지 설정은 판정 조각에 있음**

- 각 판정 조각이 데미지 GE(`DamageEffectClass`)와 계수(`DamageCoefficient`, 기본 1.0)를 가짐. 공격 어빌리티 BP 에서 조각을 펼쳐 설정함.
- AI 공격처럼 한 어빌리티가 여러 조각을 가지면 **판정마다 위력을 따로** 줄 수 있음 (예: 근접 베기 1.0 · 충격파 1.5).

**데미지 계산식 (`UCBDamageExecCalc`)**

```
최종 데미지 = max(공격력 × 계수 − 방어력, 1)
```

- **공격력** - 시전자의 `AttackPower`. 무기를 등록할 때 무기 데이터의 데미지 값이 공격력 GE 로 더해지고, 레벨업 카드 · 버스트 버프도 모디파이어로 더해짐. **스펙을 만드는 순간 값**을 씀.
- **방어력** - 피격자의 `DefensePower`. **맞는 순간 값**을 씀.
- 최소 1 - 방어력이 공격력보다 높아도 0 이 되지 않음.
- 계수는 서버가 스펙에 SetByCaller 로 실음 - 클라이언트가 보내는 것은 '누구를 맞췄는가'뿐이라 피해량을 조작할 수 없음.

| 판정 | 스펙을 만드는 때 | 적용 |
|---|---|---|
| 무기 트레이스 | 검증된 히트 이벤트를 받은 순간 | `Auth_ApplyDamageToTarget()` |
| 영역 | 판정 노티파이 순간 | 〃 |
| 투사체 | **발사 순간** (`MakeDamageSpec`) | 명중 시 `Auth_ApplyDamageSpecToTarget()` |

- 투사체는 발사 때 만든 스펙을 들고 날아가므로, 날아가는 동안 공격력이 바뀌어도(버스트 종료 등) **발사 시점의 공격력**으로 맞음.

**데미지 이후 (서버 · AttributeSet)**

- 체력을 0 ~ 최대 체력으로 고정하고, 0 이 되면 사망 이벤트를 발행함.
- 피격 반응은 **GE 가 `Effect.HitReact` 태그를 가진 경우만** 발행함 (Opt-in) - 지속 데미지 · 환경 데미지는 체력만 깎고 경직을 일으키지 않음.
- 실제로 깎인 체력(막타의 초과분 제외)을 공격한 플레이어의 PlayerState 에 누적함 - 매치 클리어 화면의 '내 데미지'.
- 피격 큐 태그는 판정마다 정함 - 무기 트레이스는 무기 데이터의 `HitCueTag`, 영역 · 투사체는 조각의 `HitCueTag`. 타격 지점을 함께 싣고, 무기 트레이스는 표면 재질까지 실어 살 · 금속별 연출을 가름.

#### ⚠️ 데미지는 타겟 하나씩 적용함

히트가 배칭되어 **한 이벤트에 여러 피격자가 실려 옴.** 그래서 루프를 돌면서 **그 회차의 타겟 하나만 담은 핸들**을 만들어 적용함.

- 핸들 전체를 넘기면 GE 가 그 핸들의 *모든* 타겟에 적용되므로, 타겟 수만큼 도는 루프에서 N² 번 적용되어 **각자 N 배 데미지**를 받게 됨.
- 한 명만 때리면 1×1 이라 증상이 드러나지 않아, 다수를 한 번에 맞히기 전까지 발견하기 어려운 종류의 버그였음.
- 그래서 이 처리를 각 판정이 아니라 **공용 함수 안에** 넣음 - 판정 종류가 늘어도 같은 실수를 반복하지 않음.
