## 5 입력 시스템

### 5.1 입력 시스템 구조

<img src="../img/Input/입력시스템구조.png" width="750">

**무엇을 쓸지는 데이터 에셋이 선언하고, 어떻게 묶을지는 입력 컴포넌트가, 언제·어떻게 처리할지는 매니저가 정함.**

- 플레이어의 모든 입력(`InputAction`)은 입력 태그(`Input.*`)와 함께 바인딩함.
- 입력은 두 갈래로 나뉨.
  - **일반 입력** — 이동·시점·줌처럼 태그 하나에 전용 콜백 하나
  - **어빌리티 입력** — 태그가 활성화 단계까지 그대로 실려 감
- 입력 태그 하나가 선언 → 바인딩 → 활성화까지 그대로 흘러가므로, **어빌리티가 늘어도 바인딩 코드는 그대로임.**

### 5.2 입력 데이터 에셋 (Input Config)

<img src="../img/Input/입력데이터에셋.png" height="500">

**플레이어의 모든 입력을 하나로 관리하고, 그대로 로드아웃에 등록하면 알아서 적용**

**IMC 등록**

- 여러 개 등록 가능 (우선 순위 설정)

**하나의 입력 태그에 Input Action 과 Trigger 방식을 같이 설정**

- 하나로 묶어서 입력 컴포넌트에 바인딩함.

**일반 입력과 어빌리티 입력을 나눠서 등록**

- 일반 입력은 트리거 단계(눌림/유지/뗌 등)까지 데이터에서 지정함. (입력마다 필요한 시점이 달라서)
- 어빌리티 입력은 트리거 단계를 쓰지 않음. (GAS 가 눌림/뗌 두 신호로 설계되어 있어 그 두 단계로 고정함)
- 에디터에서 저장할 때 태그 유효성·중복, 액션·컨텍스트 누락을 검사함. (데이터 실수를 런타임까지 끌고 가지 않게)

### 5.3 입력 컴포넌트

<img src="../img/Input/입력컴포넌트.png" width="750">

**⭐ [엔진의 기본 입력 컴포넌트를 커스텀한 이유]**

**엔진 기본 컴포넌트로는 입력과 입력 태그를 함께 묶을 수 없어서, 태그를 받는 바인딩 함수를 새로 제공하기 위함.**

- 상태(멤버 변수)를 갖지 않는 바인딩 전용 도구임. 무엇을 어디에 묶을지는 호출하는 쪽(매니저)이 정함.
- 프로젝트 설정의 기본 입력 컴포넌트 클래스로 지정해, 폰이 만드는 입력 컴포넌트가 항상 이 타입이 되게 함.
- 일반 입력은 태그로 조회해 콜백 하나에 1:1 로 묶고, 어빌리티 입력은 배열 전체를 눌림·뗌에 일괄로 묶음.

`BindAction` 의 가변 인자에 입력 태그를 실어 보내면 콜백이 그 태그를 매개변수로 받음 — **어빌리티 입력이 콜백을 늘리지 않는 이유.**

```
EnhancedInputComponent->BindAction(
    const UInputAction* Action,       // 1. 어떤 액션인지 (에셋 포인터)
    ETriggerEvent TriggerEvent,       // 2. 언제 실행할지 (눌렀을 때, 떼었을 때)
    UserObject,                       // 3. 누가 실행할지 (보통 this)
    Func,                             // 4. 콜백 함수 (함수 포인터)
    ...Varargs                        // 5. (선택) 추가로 넘길 매개변수들 — 여기에 입력 태그를 실음
);
```

### 5.4 입력 태그로 어빌리티 활성화

<img src="../img/Input/입력태그어빌리티.png" width="750">

**어빌리티마다 콜백을 만들지 않고, 태그로 찾아 활성화함.**

1. 로드아웃이 어빌리티를 부여할 때 **어빌리티 스펙에 입력 태그를 동적으로 붙임**
2. 입력이 오면 ASC 가 그 태그와 정확히 일치하는 스펙을 찾음
3. 비활성이면 활성화를 시도하고, **이미 활성 중이면 눌림 신호만 전달**해 홀드 상태를 갱신함
   - 이때 예측키와 함께 서버로 복제해서, 서버 인스턴스와 입력 대기 태스크가 같은 신호를 받게 함
4. 뗄 때도 같은 경로로 스펙과 활성 인스턴스에 알림 — 질주·연속 공격처럼 홀드로 유지되는 어빌리티가 여기서 종료를 판단함

새 어빌리티를 추가할 때 **데이터 에셋에 입력 태그만 등록**하면 되고, 바인딩과 콜백은 건드리지 않음.

### 5.5 입력 셋업과 잠금

<img src="../img/Input/입력셋업과잠금.png" width="750">

**세 신호가 순서에 상관없이 도착하고, 조건이 채워진 문부터 열림.**

입력 설정은 로드아웃이 비동기로 주입하고, 입력 컴포넌트는 폰이 만들어 넘겨줌. **둘의 완료 순서가 보장되지 않아서**, 양쪽 진입점이 같은 함수를 호출하고 준비된 것부터 처리하도록 했음.

| 진입점 | 필요한 것 | 비고 |
|---|---|---|
| 액션 바인딩 | 입력 설정 + 입력 컴포넌트 + 플레이어 컨트롤러 | 한 번만 수행. 미리 묶어도 무해함. (매핑 컨텍스트가 없으면 트리거 자체가 발생하지 않음) |
| 매핑 컨텍스트 등록 | 입력 설정 + 게임플레이 입력 허용 + 컨트롤러 | 입력 컴포넌트는 필요 없음. 데이터에 적힌 우선순위대로 등록 |

- 로비처럼 캐릭터를 조작하지 않는 레벨에서는 매핑 컨텍스트를 **아예 붙이지 않음.** (UI 가 입력을 걷어내주지 않아도 조작이 성립하지 않음)
- 잠금은 종류마다 막는 범위가 다름.

| 잠금 | 막는 범위 | 풀리는 시점 |
|---|---|---|
| 매핑 컨텍스트 미등록 | 입력 자체가 발생하지 않음 | 게임플레이 입력 허용 |
| 시스템 준비 전 잠금 | 이동 입력 | 캐릭터 준비 완료 |
| 피벗 잠금 | 이동 입력만 (시점·줌·어빌리티는 유지) | 개이트별 잠금 시간 경과 |

### 5.6 이동 입력 처리

**입력 매니저는 카메라 기준 의도만 계산하고, 실제 이동·회전 규칙은 각 컴포넌트가 가짐.**

1. 카메라 기준으로 이동 입력 방향(플레이어 의도)을 계산함
2. 그 방향으로 피벗을 판정함 - 급반전이면 이번 입력을 버리고 이동 입력을 잠금
3. 계산한 방향을 회전 컴포넌트에 넘김 (질주 시 회전 타겟으로 사용)
4. 이동은 캐릭터가 현재 향한 방향 기준으로 적용함 - 질주는 정면 직진, 그 외는 전후·좌우 분해

- 시점과 줌 입력은 카메라 컴포넌트로 위임하고, 매니저가 직접 처리하는 건 이동뿐임.
- 🔎 피벗 판정 기준(속도·각도 임계)과 잠금 시간은 개이트별 이동 데이터에서 옴 → [4.6 피벗](04-locomotion-system.md#46-피벗--급반전-처리)
- 🔎 개이트별 이동·회전 규칙 전체는 [4 이동/로코모션 시스템](04-locomotion-system.md) 참고
